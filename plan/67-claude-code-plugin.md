# 67 — Package nexus as a Claude Code plugin

> `/plugin install nexus` collapses adoption's Step 1 (clone +
> copy + replace) into one command, while the client-agnostic
> `skills/` layout stays the canonical source — the plugin
> wraps it, never replaces it.

## Why

`templates/README.md`'s TL;DR for adopting nexus is clone the
kit repo, copy `templates/` into the target repo, replace the
placeholders. That is the whole onboarding path today, and it
is heavier than it needs to be now that Claude Code supports
plugins and marketplaces: a repo can ship its own
`.claude-plugin/marketplace.json` and let an adopter run
`/plugin install` directly. The nexus repo is already its own
distribution channel (push = publish, per the versioned
releases work in spec 61), so hosting its own marketplace entry
costs nothing new to operate.

The plugin must not become a second, divergent copy of the
skill family: `skills/` (this repo's own loop) and
`templates/skills/` (what adopters copy) stay the single
source of truth, and the adopted-skills doctrine — an adopter
owns and edits their copy — must survive. So the plugin ships
narrowly: three commands (adopt, upgrade, doctor) that wrap the
canonical `prompts/` text and the versioned `templates/`
snapshot, not the skills themselves.

Claude Code v2.1.269 (2026-09-11) shipped `claude plugin eval`,
a first-party command that runs a plugin's eval suite and
returns scored, reproducible results. That closes the one gap
this candidate sat on since July: a byte-diff verify leg can
prove the plugin *build* is reproducible, but only an eval
suite proves the three shipped commands actually behave
correctly once installed.

## Design

- `.claude-plugin/marketplace.json` at the repo root, listing
  nexus as its own single-plugin marketplace entry (name,
  version, source), so `/plugin marketplace add
  daretodave/nexus` then `/plugin install nexus` works straight
  from this repo with no separate hosting.
- `plugin/` generated by a new `scripts/build-plugin.mjs`,
  never hand-edited (same discipline as `assets/`): its
  `plugin.json` version tracks `plan/nexus.lock`'s `version`
  field, and it vendors a snapshot of `templates/` at that
  version for offline, deterministic installs (an adopter's
  plugin install never depends on this repo's working tree
  moving under it).
- Three commands only, each a thin wrapper that shells out to
  the canonical `prompts/` text (`prompts/adopt.md`,
  `prompts/upgrade.md`) plus one new `doctor` prompt:
  - `adopt` — runs the `templates/` copy + placeholder-replace
    flow `prompts/adopt.md` already describes, against the
    vendored snapshot.
  - `upgrade` — runs `playbooks/upgrade.md`'s version-bump flow
    against `prompts/upgrade.md`.
  - `doctor` — a new read-only check (new `prompts/doctor.md`)
    that reports an adopted repo's drift against its
    `plan/nexus.lock` pinned version, no writes.
  - The skill family (`skills/`, `templates/skills/`) is never
    wrapped: a plugin command is a one-shot operation, not a
    loop, and the adopted-skills doctrine requires the
    adopter's own copy stay editable outside any plugin update
    path.
- A new verify leg (`node scripts/verify.mjs`, a `plugin` leg)
  regenerates `plugin/` in memory from `build-plugin.mjs` and
  byte-diffs it against the committed tree — any drift between
  the generator and the committed output is a hard gate
  failure, the same contract `assets/`'s diagrams already use.
- A `claude plugin eval` suite (new `plugin/eval/` or
  `.claude-plugin/eval/`, whichever the installed Claude Code
  version's scaffolding expects) exercising the three commands
  against a scratch adopter repo: adopt installs a clean
  template tree, upgrade bumps a pinned-old fixture forward one
  version, doctor correctly flags a deliberately drifted
  fixture. This is what actually proves command behavior, not
  just build reproducibility.
- `playbooks/plugin.md`: what the plugin is, what it
  deliberately does not ship (the skill family), how
  `build-plugin.mjs` keeps it in sync, and how the eval suite
  is run and read.
- `templates/README.md`'s TL;DR gets a `/plugin install nexus`
  fast path alongside (not replacing) the clone-and-copy path,
  since not every adopter runs Claude Code or wants the plugin
  install surface.

## Acceptance

- **A1** `.claude-plugin/marketplace.json` exists at the repo
  root and `/plugin install nexus` installs cleanly from this
  repo with no external hosting step.
- **A2** `plugin/` is generated-only (never hand-edited) by
  `scripts/build-plugin.mjs`, versioned from `plan/nexus.lock`,
  and vendors an offline `templates/` snapshot at that version.
- **A3** The plugin ships exactly three commands — adopt,
  upgrade, doctor — each wrapping canonical `prompts/` text;
  the skill family (`skills/`, `templates/skills/`) is not
  wrapped or duplicated by the plugin.
- **A4** `node scripts/verify.mjs`'s new `plugin` leg
  regenerates `plugin/` in memory and byte-diffs it against the
  committed tree, hard-failing on drift.
- **A5** A `claude plugin eval` suite exercises adopt, upgrade
  and doctor against scratch fixtures and returns a scored,
  reproducible result; it is wired into CI alongside
  `node scripts/verify.mjs`.
- **A6** `playbooks/plugin.md` documents the plugin's scope,
  its generator, and how to run and read the eval suite;
  `templates/README.md`'s TL;DR links the `/plugin install`
  path.

## Open questions

- Where `claude plugin eval`'s suite scaffolding actually lives
  (`.claude-plugin/eval/` vs. a path the installed Claude Code
  version's own tooling expects) is deliberately left to the
  first chunking session — it needs a read of the current
  `claude plugin eval` docs at chunking time, not a guess
  frozen into this spec.
- Whether `doctor`'s drift check can reuse
  `scripts/plan/support.mjs` or `scripts/secrets-audit.mjs`
  machinery, or needs its own, is left to the same session.
