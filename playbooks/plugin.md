# Playbook: plugin (`/plugin install nexus`)

> `/plugin marketplace add daretodave/nexus` then `/plugin
> install nexus` installs three thin commands — `/adopt`,
> `/upgrade`, `/doctor` — plus an offline snapshot of
> `templates/`, as a faster on-ramp beside the clone-and-copy
> path `templates/README.md` documents. The skill family
> (`skills/`, `templates/skills/`) is never part of the
> install: once copied, an adopter owns and edits their own
> skills, and a plugin command is a one-shot operation, never
> a loop.

---

## Install

```
/plugin marketplace add daretodave/nexus
/plugin install nexus
```

The first command points Claude Code at this repo's own
`.claude-plugin/marketplace.json` — a single-plugin
marketplace entry naming `nexus` at `./plugin`, so the repo
hosts its own distribution with no external registry. The
second installs what that entry names: `plugin/
.claude-plugin/plugin.json` (name, version, author), three
commands under `plugin/commands/`, and an offline
`plugin/vendor/` snapshot — `templates/`, the canonical
`prompts/adopt.md`, `prompts/upgrade.md`, `prompts/doctor.md`
and `scripts/plugin-doctor.mjs` — byte-for-byte as they stood
in this repo when `scripts/build-plugin.mjs` last ran.

## Scope — what the three commands do

| Command | Wraps | Does |
|---|---|---|
| `/adopt` | `prompts/adopt.md` | Copies the vendored `templates/` snapshot into the target repo and sweeps the placeholders — the clone+copy+replace flow, against offline files instead of a second checkout. |
| `/upgrade` | `prompts/upgrade.md` | Runs the version-bump flow this kit's own [`upgrade.md`](./upgrade.md) describes, against the vendored prompt text. |
| `/doctor` | `prompts/doctor.md` + `scripts/plugin-doctor.mjs` | Read-only: compares the target repo's `plan/nexus.lock` version against the version this install ships, reports `current` / `behind` / `ahead` / `not-adopted` / `unreadable`. No writes, ever. |

Each command's body (`plugin/commands/<name>.md`) is a few
lines: "read `${CLAUDE_PLUGIN_ROOT}/vendor/prompts/<name>.md`
and follow it exactly." `doctor`'s body also redirects the one
script path its prompt names to the vendored copy,
`${CLAUDE_PLUGIN_ROOT}/vendor/scripts/plugin-doctor.mjs`,
since an installed plugin has no `../nexus` checkout to read
that script from otherwise. Nothing else ships under
`/plugin`: no `/march`, no `/next`, no `/iterate`. The plugin
surface is these three commands and nothing wider.

## What it deliberately doesn't ship

The skill family — `skills/` (this repo's own loop) and
`templates/skills/` (what an adopter copies) — is never
wrapped, vendored, or exposed as a plugin command. Two reasons,
both load-bearing:

1. **A plugin command is a one-shot operation.** `/adopt`,
   `/upgrade` and `/doctor` each run once and stop. The skill
   family is the opposite: `/march`, `/next`, `/iterate` and
   the rest are a standing loop meant to run every tick, across
   months, reading and writing `plan/` state between runs.
   Collapsing a loop into one plugin invocation would
   misrepresent what it is.
2. **The adopted-skills doctrine.** Once copied, `skills/` and
   `.claude/commands/` are the adopter's own files — edited,
   extended with project lanes
   (`customization/project-lanes.md`), carried forward by this
   kit's own [`upgrade.md`](./upgrade.md) three-way merge,
   never silently replaced. `concepts/architecture.md` draws
   the same split for this repo itself: `skills/` is what nexus
   runs, `templates/skills/` is what an adopter gets — "same
   shapes, different verbs." A plugin command that re-ran or
   re-synced the skill family on every invocation would break
   that ownership: there would be no way to tell an adopter's
   edit from the plugin's own next write.

Any work that still needs the skill family — shipping a
chunk, running `/march`, auditing with `/iterate` — stays on
the clone-and-copy path `templates/README.md` documents. The
plugin only shortens that path's first step.

## How `build-plugin.mjs` keeps it in sync

`plugin/`, `plugin/vendor/` and `.claude-plugin/
marketplace.json` are entirely generated by
`scripts/build-plugin.mjs` — never hand-edited, the same
discipline `assets/`'s diagrams already carry. Running it with
no flags regenerates the whole tree from two sources:

- **`plan/nexus.lock`'s `version:` line** becomes `plugin/
  .claude-plugin/plugin.json`'s `version` field. The plugin's
  own version tracks the kit's, with no second number to keep
  in sync by hand.
- **`templates/`, `prompts/{adopt,upgrade,doctor}.md` and
  `scripts/plugin-doctor.mjs`** are copied byte-for-byte into
  `plugin/vendor/` — a frozen snapshot, not a live reference.
  An install never depends on this repo's working tree moving
  under it: `/adopt` run five minutes after a release reads the
  same bytes as `/adopt` run a year later against that same
  release, even as this repo's own `templates/` keeps changing
  underneath.

`--check` regenerates the tree in memory and diffs it against
disk without writing, naming every file that differs; `--root
<path>` points either mode at a tree other than this repo (the
gate's own use, below). Two runs on an unchanged tree produce
byte-identical output — sorted file lists, `\n` line endings,
no timestamps — so `plugin/`'s git history only ever shows a
real content change, never incidental churn.

## The verify gate's `plugin` leg

`node scripts/verify.mjs`'s `plugin` leg runs
`scripts/build-plugin.mjs`'s `render()` in memory and
byte-diffs every file it produces against the committed
`plugin/` and `.claude-plugin/marketplace.json` trees, plus
`scripts/__tests__/build-plugin.test.mjs`'s own suite. Any
drift — a stale file left on disk, a hand edit, a generator
change nobody re-ran — is a hard gate failure naming the exact
file. There is no override: the fix is always "run `node
scripts/build-plugin.mjs`, then commit what it wrote."

## The eval suite — not yet built

Chunk 67.4 of
[`plan/67-claude-code-plugin.md`](../plan/67-claude-code-plugin.md)
specifies a `claude plugin eval` suite under `plugin/evals/`
that exercises `/adopt`, `/upgrade` and `/doctor` against
scratch fixtures — a clean install, a pinned-old version bump,
a deliberately drifted repo — and runs in CI alongside `node
scripts/verify.mjs`. As of this writing that chunk is **not
built**: there is no `plugin/evals/` directory yet, and the
three commands above are proven only by the `plugin` leg's
byte-diff (the generator produces what it should) and by
hand-running them — not by a scored eval pass. When 67.4
ships, this section should describe the suite's actual run
command, its report shape, and how to read a failing eval;
read that chunk's own build before trusting any eval-suite
claim here that predates it.
